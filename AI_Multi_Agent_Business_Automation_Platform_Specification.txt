AI MULTI-AGENT BUSINESS AUTOMATION PLATFORM
Unified Project Specification & Architecture Document
Production-ready cloud-native platform • Google Cloud • Laravel CRM • Vue Frontends • Minimal AI Usage
1. Назначение проекта
Создать cloud-native платформу для автоматизации продаж, работы с клиентами, корпоративных знаний, записи на услуги, оплаты и маркетинговой аналитики. Архитектура является мультиагентной и микросервисной: AI-агенты используются только там, где требуется обработка неструктурированного текста, генерация или интеллектуальная интерпретация. Обычные бизнес-операции выполняются специализированными алгоритмическими сервисами без LLM.
Платформа должна быть production-ready, modular, secure, scalable и AI-readable. Каждый сервис должен быть независимо разворачиваемым, тестируемым и обновляемым.
2. Ключевые архитектурные принципы
● Микросервисная архитектура вместо монолита.
● Разделение AI Agents и обычных Backend Services.
● Минимизация использования LLM для снижения стоимости эксплуатации.
● Google Cloud как основная cloud-платформа.
● Google Workspace как корпоративная среда документов и знаний.
● Google Drive/Docs - источник корпоративной базы знаний; RAG использует её актуальное содержимое.
● Laravel - корпоративный CRM и бизнес-портал.
● Vue - отдельные frontend/landing-проекты.
● Google Calendar - через отдельный Booking Service, а не напрямую из AI-агента.
● Snowflake - центр аналитики, а не операционная база данных.
● Все интеграции через API и чёткие сервисные контракты.
● Docker-контейнеризация и независимые CI/CD pipelines.
● Clean Architecture, SOLID, строгая типизация, автоматические тесты и security-by-design.
3. AI-компоненты и обычные сервисы
3.1. AI Agents
● WhatsApp Sales Agent - клиентская коммуникация, RAG, рекомендации, сбор лидов.
● Knowledge Agent - обработка неструктурированных внутренних знаний и подготовка обновлений базы знаний.
● Meeting Intelligence Agent - обработка транскриптов встреч, извлечение решений, задач и требований.
● Marketing AI - генерация предложений/акций на основе подготовленной аналитики.
● RAG Agent/Layer - интеллектуальный поиск и контроль источников для AI-компонентов.
3.2. Algorithmic Services
● API Gateway
● Auth Service
● CRM Service
● Booking Service
● Payment Service
● Competitor Scraper Service
● Marketing Analytics Service
● Analytics Service
● Snowflake Connector Service
● Notification Service
● File Service
● Knowledge/Indexing Service
● Landing/API services
Competitor Scraper Service не является AI-агентом: он выполняет обычный scraping, parsing, поиск компаний и сбор данных. Аналогично Booking, Payment, CRM, ETL, Calendar, notification и аналитические операции не должны вызывать LLM без отдельной необходимости.
4. Основные пользовательские каналы
4.1. WhatsApp
● WhatsApp Business Cloud API принимает сообщения клиентов.
● Sales Agent определяет намерение и при необходимости вызывает RAG.
● Agent отвечает на вопросы о продуктах, услугах, ценах и условиях.
● Agent собирает данные лида и передаёт их в CRM.
● Для записи Agent обращается к Booking Service.
● Для оплаты Agent/Frontend обращается к Payment Service только для продуктов/услуг, где действительно предусмотрена онлайн-оплата.
4.2. Landing Pages
● Lead Landing - заявка, обратный звонок, консультация.
● Booking Landing - запись на услугу или встречу.
● Sales Landing - покупка и онлайн-оплата.
● Landing может содержать WhatsApp Widget и AI Chat Widget.
4.3. Internal Telegram
Telegram используется как внутренний канал согласования и передачи информации. Отдельный Telegram Service/Knowledge Agent работает с внутренними группами. Telegram также используется для согласования сгенерированных маркетинговых предложений перед публикацией.
5. AI Agents
5.1. WhatsApp Sales Agent
● Приём сообщений через WhatsApp Business API.
● Определение намерения клиента.
● RAG-поиск по корпоративной базе знаний.
● Ответы на вопросы о продуктах, услугах, ценах и FAQ.
● Рекомендации продуктов.
● Сбор имени, телефона, email, компании, интересующего продукта и комментария.
● Создание/обновление лида через CRM API.
● Вызов Booking Service при необходимости записи.
● Вызов Payment Service только если конкретный сценарий поддерживает оплату.
Sales Agent не изменяет Knowledge Base напрямую.
5.2. Telegram Knowledge Agent
● Подключение к внутренним Telegram-группам.
● Выделение полезной бизнес-информации: продукты, цены, FAQ, инструкции, решения менеджеров, клиентские ответы и изменения.
● Передача структурированных данных в Knowledge Service/Knowledge Agent.
● Не должен самостоятельно публиковать непроверенные изменения в публичную базу знаний.
5.3. Google Meet Intelligence Agent
● Получение доступных транскриптов Google Meet.
● Извлечение решений, задач, изменений продукта, требований клиентов и договорённостей.
● Формирование структурированного knowledge update.
● Передача результата в Knowledge Service.
5.4. Marketing AI
● Получает только подготовленные агрегированные данные от Marketing Analytics Service.
● Формирует варианты акций, предложений или маркетинговых сообщений.
● Передаёт предложение в Telegram для согласования.
● После утверждения предложение передаётся в CRM/Landing Services.
● Результаты кампании возвращаются в Snowflake для следующего аналитического цикла.
6. Knowledge Base и RAG
Google Drive является корпоративным хранилищем документов. Google Docs используется для редактируемого содержимого. База знаний включает каталог продуктов, цены, инструкции, техническую документацию, FAQ, sales materials, policies и marketing materials.

RAG должен сохранять метаданные источника и обеспечивать возможность определить, из какого документа и фрагмента получен контекст.
7. CRM
Laravel CRM является основной операционной системой управления клиентами и продажами.
● Leads
● Customers
● Products
● Sales Pipeline
● Managers
● Interactions / communication history
● Bookings
● Payments
● Promotions
● AI Agent logs
● Knowledge Base viewer
● Analytics dashboards
● Lead source and promotion attribution
● Customer status, включая new/repeat customer
CRM не является заменой Snowflake. Операционные данные хранятся в PostgreSQL/Laravel, а аналитические данные и исторические события передаются в Snowflake.
8. Booking Service и Google Calendar
Booking Service является отдельным микросервисом. AI-агенты и frontend не работают с Google Calendar напрямую.
● Получение свободных слотов.
● Создание записи.
● Отмена.
● Перенос.
● Синхронизация с Google Calendar.
● Напоминания.
● Проверка конфликтов.
● API для CRM, Landing и AI Sales Agent.
9. Payment Service
Оплата является опциональным бизнес-сценарием. Не каждый landing или promotion должен иметь кнопку оплаты.
● Sales Landing может использовать Payment Service.
● Booking Landing использует Booking Service без обязательной оплаты.
● Lead Landing может создавать лид без оплаты.
● Payment events передаются в CRM и Snowflake.
● Платёжная логика изолирована от Sales Agent и frontend.
10. Competitor Scraper Service
Competitor Scraper Service - обычный алгоритмический микросервис без LLM.
● Получение координат/географической области.
● Поиск компаний и конкурентов.
● Использование Google Maps и доступных внешних источников.
● Загрузка сайтов.
● HTML parsing.
● Извлечение цен, услуг, акций и других структурируемых данных.
● Нормализация данных.
● Передача результатов в Snowflake.
● Плановый запуск через Scheduler.

Snowflake не используется как основная OLTP-база CRM или Booking Service.

19. AI Usage Policy
LLM является дорогим ресурсом и не должен использоваться для задач, которые надёжно решаются обычным кодом.
Без AI
● Scraping and HTML parsing
● Company search
● Google Maps integration
● ETL
● CRM writes
● Calendar operations
● Payment operations
● PDF generation
● Notifications
● API integrations
● Data validation and deterministic transformations
● Snowflake loading and aggregation
С AI
● Customer answers where natural-language interpretation is required
● Meeting transcript processing
● Extraction of knowledge from unstructured text
● Marketing offer generation
● Large-document summarization
● Other tasks where deterministic algorithms are insufficient
20. Copilot / AI-readable Requirements
● Использовать официальные SDK и API, прежде всего официальный Google ADK и актуальные Google APIs.
● Не использовать устаревшие API или неофициальные библиотеки без явной необходимости.
● Сохранять модульность и границы сервисов.
● Не добавлять LLM в обычный бизнес-сервис без обоснования.
● Следовать SOLID, Clean Architecture и DDD там, где это оправдано.
● Использовать строгую типизацию и понятные интерфейсы.
● Публичные классы, функции, сервисы, tools и agents должны иметь docstrings.
● Каждый сервис должен иметь README с назначением, API, конфигурацией и запуском.
● Контракты между сервисами должны быть явно описаны через OpenAPI/JSON Schema.
● Секреты запрещены в коде и git.
● Перед добавлением новой зависимости проверять, существует ли официальное или уже используемое решение.
● Критическая бизнес-логика должна иметь автоматические тесты.
● Изменения должны быть локальными и не нарушать границы сервисов.
